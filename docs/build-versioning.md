# Версии сборок

Главное меню показывает версию из `package.json` и число коммитов текущей сборки.
Например: `v0.1.0 · сборка 284`. Подсказка содержит полный идентификатор
`0.1.0+build.284.391f2d9` и ветку.

`GET /api/build` вычисляет данные из рабочего дерева, которое обслуживает
`tools/serve.py`. После слияния и перезагрузки страницы номер обновляется
автоматически. Уже открытая игра сохраняет прежнюю подпись до перезагрузки,
поскольку её код ещё не обновился. Незакоммиченные изменения отмечаются как
«локальные правки», чистая ветка вне `main` — как «предпросмотр».

Git-тег `v0.1.0` закрепляет первую явно пронумерованную одобренную сборку
`391f2d9` (№284). Последующие коммиты имеют собственный номер сборки;
тег остаётся на исходном релизе. Теги релизов не перемещать и не перезаписывать.

- Исправления: PATCH, например `0.1.0` → `0.1.1`.
- Новые возможности: MINOR, например `0.1.1` → `0.2.0`.
- Несовместимые изменения: MAJOR, например `0.2.0` → `1.0.0`.

После каждого завершённого набора изменений, до слияния, повысить версию
в `package.json` и корневых записях `package-lock.json` через
`npm version patch --no-git-tag-version` (либо `minor`/`major`).
Исправления, тексты, озвучка и небольшие изменения интерфейса повышают PATCH;
новые игровые возможности и миссии — MINOR; несовместимые изменения — MAJOR.
Промежуточные сохранения файлов отдельной версии не требуют.
Автоматическое изменение номера сборки из Git не заменяет этот шаг.
После одобренного слияния поставить аннотированный тег на точный коммит `main`.

Старый `campaign/previews/build-info.json` — сохранённый паспорт первой
сборки, а не источник актуального номера в меню.
