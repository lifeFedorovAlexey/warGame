# Измерения Damage System — 7 ноября 2026

Исторический прогон 1280×720: `2026-11-07T12:47:06.046Z`. Полные значения, p95/max, число выборок, версии и SHA-256 измеренных исходников: [damage-benchmark.json](measurements/damage-benchmark.json). Это измерения реального WebGL в существующей сцене кампании, а не расчёт ожидаемого FPS. Последний повтор после исправлений, при выбранном разрешении **1920×1080**, находится в [отдельном отчёте](performance-1080.md).

## Условия

- Windows, AMD Ryzen 9 7900X (12 ядер, 24 логических потока), NVIDIA GeForce RTX 4070. CPU определён из `HKLM/HARDWARE/DESCRIPTION/System/CentralProcessor/0/ProcessorNameString`, GPU подтверждён WebGL renderer и CDP SystemInfo.
- Edge `157.0.4341.42`, headless, ANGLE D3D11, WebGL2; **аппаратный RTX 4070**, не SwiftShader. Node `v24.22.0`.
- 1280 × 720, pixel ratio 1; автоматическое уменьшение разрешения отключено. Обычные рельеф, освещение, тени и материалы кампании.
- 90 кадров прогрева, затем по 6 секунд на `settled` (повреждения уже есть, новых нет) и `impacts` (синхронное попадание в каждую машину каждые 500 мс).
- Перед замером каждой включённой сцены: боковой удар мощностью 110 и очередь из восьми пуль в каждую машину. В измеряемой фазе удар мощностью 22, направления чередуются. HP увеличен только в тестовом fixture, чтобы все машины дожили до конца.
- Все N машин действительно представлены в кадре; это проверяется assertion. Камера отдаляется с увеличением сетки: 1/10 — ближний LOD, 50/100 — средний, 200 — 117 средних и 83 дальних. Результат 200 нельзя выдавать за 200 близких машин максимальной детализации.
- Симуляция AI, поиск пути и движение **приостановлены**, чтобы выделить представление и обработку повреждений. Это не замер полного боя 200 автономных юнитов. Движение/бой/строительство проверяются отдельно штатными тестами миссии.
- `off` отключает обработку попадания и шейдерное представление повреждений. Общие подготовленные модели, instancing и выделенный атлас остаются. Это сравнение runtime-переключателя в одной версии приложения, не сравнение всего приложения с историческим commit без модуля.

FPS вычислен из интервалов `requestAnimationFrame` и ограничен примерно 60 Гц. Значения около 60 не показывают максимальную пропускную способность видеокарты. CPU — `performance.now()` вокруг обработки пачки попаданий и `world.update`, включая подготовку render-команд; p95 и максимумы приведены отдельно. GPU — асинхронные `EXT_disjoint_timer_query_webgl2` вокруг измеряемого обновления/рендера; disjoint делает значение недействительным. В этом прогоне disjoint не зарегистрирован. Это elapsed GPU interval, не отдельная стоимость шейдера повреждений; его нельзя складывать с CPU как последовательное время кадра.

Во всех спокойных сценариях: **0 обновлений геометрии, 0 обновлений матричного instance buffer, 0 загрузок строк повреждений**. Счётчик геометрии проверяет версии реальных position BufferAttribute, а не возвращает константу. Работа GPU по деформации видимых вершин при этом продолжается.

## Память

Снимки после `impacts`, MiB. RAM — сумма `PrivateMemorySize64` процессов **запущенного тестового браузера**; working set также сохранён в JSON. VRAM — сумма `DedicatedUsage` Windows `GPU Process Memory` по этим PID. Это память всего браузера с картой и renderer, а не исключительно Damage System и не доказательство физической резидентности каждого ресурса на GPU. Shared GPU memory записана отдельно в JSON. WebGL `renderer.info.memory` сообщает количество ресурсов, не их точный размер в байтах.

Сценарии идут последовательно в одном браузере: GC, освобождение вспомогательных процессов и кэширование объясняют, почему некоторые `on` снимки меньше `off`. Эти разности нельзя считать точной стоимостью одного повреждённого объекта. Лимиты собственных буферов известны из их размеров; для точного attributable GPU allocation потребовался бы отдельный драйверный профилировщик.

## Физические объекты и ограничения сценария

Во время измеряемых фаз активных обломков — **0**: начальное повреждение уже прогрето, последующие удары направлены в кузов. Это намеренный замер массовых повреждений, а не одновременного отрыва всех деталей. Отрыв колеса, фары, защитной конструкции и оружия, а также элементов четырёх зданий проверяется браузерным smoke-тестом. Отдельный автоматический тест многократно пытается создать 50 обломков, подтверждает максимум 24 активных, засыпание, максимум 64 сохраняемых и удаление ресурсов. Из этого не следует измеренный FPS сцены с 24 летящими обломками — такой показатель здесь не заявлен.

## Исправленные проблемы

1. В раннем варианте BVH использовал слишком широкое расширение AABB, а решётка заново вычислялась для повторяющихся вершин. На 200 машинах с ударами получилось **0,64 FPS**, среднее CPU **1560,5 мс**, 6186 мс поиска 800 контактов. Сырые данные сохранены в [initial.json](measurements/initial.json). Реальный дефект исправлен: расширение по фактическому диапазону смещений, отсечение по ближайшему пересечению, кэш вычисленных вершин на один луч, BVH жёстких подвижных деталей. В финальном прогоне 2400 контактов заняли 287,6 мс.
2. Деление треугольника веером через центр порождало длинные тонкие треугольники и избыточную рекурсию. Подразделение по серединам общих рёбер сохраняет поверхность/UV/ID частей. На этапе этой оптимизации полная сцена 200 машин сократилась с **4 244 435 до 2 404 025** треугольников (−43,4%); 10 близких машин — с 1 459 524 до 417 804 (−71,4%). Это историческое сравнение: после него добавлено локальное уплотнение под остеклением для устранения пересечений при сильной деформации. Актуальное число треугольников находится в таблице спокойного состояния выше. Предыдущий прогон: [before-mesh-optimization.json](measurements/before-mesh-optimization.json).
3. Устранены безусловные загрузки матриц экземпляров в спокойном кадре. Ёмкость прежнего batch 80 заменена на 256 с ростом, поэтому 100/200 объектов не обрезаются.
4. Строки состояния обновляются по событию и видимости, шейдерные следы не создают отдельный mesh/draw call. Подготовленные атрибуты зданий общие для всех экземпляров prefab.
5. После удаления шаблонного финала добавлены передача нагрузки близким деталям и ограничение якобиана пластической решётки. Их стоимость включена в актуальную фазу `impacts`; состояние меняется только по воздействию. Подробности и отдельная визуальная проверка — [разные истории](individuality.md).

## Воспроизведение

```powershell
python tools/serve.py
# В другом терминале:
npm run check:damage
npm run check:damage:browser
npm run bench:damage
# Дополнительный неблагоприятный вариант: все 200 машин принудительно LOD0.
node tools/check-damage-browser.mjs --benchmark --all-near
```

При другом окружении задать `PLAYWRIGHT_PATH`, `EDGE_PATH`, `DAMAGE_BASE_URL`. Playwright может быть установлен в окружении инструмента; он не добавлен в runtime игры. `DAMAGE_COUNTS` и `DAMAGE_SECONDS` меняют размеры/длительность. `--software` запускает SwiftShader; его результаты необходимо подписывать отдельно. JSON сохраняется в `campaign/reports`, скриншоты — в `campaign/previews`. Скрипт останавливается при ошибках WebGL/JavaScript, невидимых fixture-машинах или лишних спокойных загрузках. Измерения не переносятся автоматически на другую видеокарту, разрешение, сотни движущихся юнитов или полный бой с AI.
