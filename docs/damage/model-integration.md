# Подключение моделей к Damage System

Система работает внутри существующей кампании. Начальные точки: `damage-state.js` (логика), `damage-geometry.js` (подготовка и контакт), `damage-shader.js` (представление), `damage-system.js` (жизненный цикл). Исходные игровые GLB не перезаписываются.

## Контракт модели

1. Сборка использует существующие координаты: Z вверх, Y вперёд; размеры в метрах модели, масштаб мира задаётся `config.worldScale`. Все LOD должны совпадать по системе координат и ID частей.
2. Каждая поверхность содержит `position`, `normal`; UV сохраняются, если присутствуют. `damagePart` — Float32 attribute с одним целым ID 0…127 на вершину. Все три вершины треугольника должны иметь один ID. На границе частей дублировать вершины, сохраняя совпадающие позиции и корректные нормали.
3. ID обозначает физическую/логическую часть, а не номер материала. Одна дверь может состоять из металла, резины и стекла; при необходимости стекло получает собственный ID. Объединение поверхностей по материалу обязано сохранять `damagePart`.
4. Перед подготовкой установить прототип в нейтральную позу и вызвать `root.updateMatrixWorld(true)`. Подготовка сохраняет матрицу привязки и координаты общей сборки. Не использовать уже размещённый в мире экземпляр как прототип.
5. `body` — деформируемый кузов; `chassis` — жёсткая рама; `weapon` / `equipment` — анимируемая жёсткая установка; `building` — неподвижная конструкция. Функция `wheelId` поддерживает текущие имена `axle_1_L_wheel` и аналогичные. Для другого рига задавать `damagePart` и явно отмечать соответствующий binding как `dynamic`/`deform=false`.
6. Новым моделям задавать границы решётки, покрывающие деформируемую оболочку. Размер решётки фиксирован 5 × 9 × 5; границы настраиваются. Очень крупной или вытянутой модели может потребоваться другая плотность/профиль воздействия — это отдельная настройка качества, а не увеличение числа узлов на каждый юнит.

Пример подготовки в адаптере модели (переменные `damage`, `node`, `kind`, `pose` предоставляет существующий слой моделей):

```js
const profile = {cageBounds: {min: [-1.6, -3.4, 0], max: [1.6, 3.4, 3.8]}};
const binding = damage.prepare(node, 'body', 0, profile);
// Для каждого primitive каждого LOD используется один и тот же profile.
mesh.geometry = binding.geometry;
const hook = damage.attach(mesh, binding, {instanced: true});
// InstancedMesh также получает instanceDamage: vec2(row, damageLod).
// Рабочая реализация выделения и роста буфера — PoseBatch в vehicle-layer.js.
damage.registerVehicle(kind, bindings, pose, {parts});
```

`bindings` для collider — комплект LOD0. `parts` — словарь `{id: {name, material, detachable, strength?}}`. Поддерживаются профили `metal`, `concrete`, `glass`, `rubber`, `equipment`. Не объявлять бетону пластичность металла. `strength` задаёт порог разрушения детали в единицах мощности существующей игры, не в джоулях.

`pose(entity)` возвращает `Map<binding, Matrix4>` для движущихся деталей. Матрица переводит координаты нейтральной сборки в текущую локальную позу: `currentNode.matrixWorld * inverse(binding.bind)`. `vehicle-layer.js:damagePose` реализует это для текущих колёс и установок. CPU-raycast и извлечение обломка используют ту же позу; шейдерная отметина остаётся в координатах исходного материала.

Границы профиля должны совпадать у всех bindings одной модели, включая жёсткие части: первое попадание создаёт состояние с границами профиля. CPU-выборка использует сохранённые `cageBounds`, GPU — uniform из binding. При изменении границ в новой версии модели требуется миграция сохранений. Нельзя молча менять значения и оставлять старую решётку.

## Части существующей Буханки

| ID | Часть и поведение |
| --- | --- |
| 0 | Оболочка: локальные вмятины, следы, нагар; не исчезает целиком |
| 1–4 | Колёса C01: отделяются, каждое уменьшает множитель скорости на 0,2, минимум 0,25 |
| 5–6 | Фары: линза разрушается, соответствующий прожектор отключается |
| 7–8 | Передняя/задняя защитная трубчатая конструкция C01: отделяется |
| 9 | Вооружение: отделяется; существующий цикл атаки блокируется |
| 10–15 | Остекление: разрушенное состояние с трещинами и затемнением |
| 16–17 | Зеркальные поверхности |
| 18–19 | Задние боковые окна, независимо от среднего окна |
| 20–21 | Боковые окна кабины, независимо от салона |

Защитные конструкции C01 уже присутствуют в исходной геометрии, но объединены с рамой по материалу. `tagC01Guards` выделяет их связные компоненты при подготовке, используя размеры из `demo/main.js`. Треугольники оболочки дверей не вырезаются эвристикой.

Стёкла также размечаются целыми связными компонентами, без разных ID на углах одного треугольника. В формате состояния v2 боковые окна разделены; `upgradeDamageState` при загрузке v1 переносит прежнее групповое разрушение на соответствующие окна и сохраняет положение следов. Уже разрушенные детали старых сохранений не восстанавливаются автоматически: полная история воздействий для пересчёта отсутствует.

Готовые варианты смятого кузова не нужны: пластические смещения вычисляются по каждому контакту. Отдельная геометрия двери нужна для её существования как отделяемой детали, а не для выбора заранее нарисованного финала. Текущие отказы креплений используют габариты исходных частей; для точных петель, шарниров и изломов потребуются дополнительные данные модели и соответствующий solver.

У `builder`, `flamer`, `command`, `raider` подключён тот же поток состояния и отрисовки. Полная автоматическая семантическая разметка произвольного GLB не обещается: новым дверям, броне и оборудованию нужны явные ID. Для нового шасси с другим количеством колёс нужно также изменить адаптер влияния повреждений на движение; текущая игровая механика использует ID 1–4. ID 9 зарезервирован под боевую установку.

## Подготовка зданий

В `prefabs.js` helper `part(name, profile, build)` оборачивает генерацию существующего элемента. Окна получают ID по позиции. В `industrial-buildings.js` размечены трубы, вентиляция, антенны и внешние установки; в `scav-prefabs.js` размечено оружие башен. При объединении примитивов атрибут сохраняется.

```js
part('roof_vent', {material: 'equipment', detachable: true, strength: 90}, () => {
  // Существующий вызов mesh/box/cylinder, без изменения размеров и материала.
});
```

В текущем генераторе ID назначаются в порядке создания, с резервированием 9 для оружия. При изменении порядка/числа элементов нужно сохранить прежнюю таблицу ID либо добавить миграцию сохранений. Реестр каждого prefab доступен в `root.userData.damageParts`; превышение 128 частей вызывает ошибку, а не тихую потерю состояния.

Один ID может представлять группу мелких окон/труб, чтобы удерживать бюджет. Для разрушаемой бетонной секции готовить отдельную замкнутую геометрию с поверхностью излома. Основа здания остаётся жёсткой. Сейчас отрыв убирает подготовленный элемент, а не генерирует произвольную новую топологию стены.

## Передача внешнего контакта

Обычная стрельба уже вызывает `Mission.damage` и точный collider. Для столкновения/нового оружия:

```js
const hit = world.damage.trace(target, worldRayOrigin, worldRayDirection);
if (hit) mission.damage(target, power, source, {...hit, type: 'collision'});
```

Типы: `bullet`, `shell`, `penetrator`, `collision`, `fire`. `power` использует существующую шкалу HP. `trace` возвращает ID объекта и детали, мировые точку/нормаль/направление, локальные координаты и координаты исходного материала. Для готового контакта физического движка нужно передать тот же контракт; нормаль поверхности и направление удара — разные величины. Повреждения не зависят от камеры. Не заменять факт столкновения приблизительным пересечением навигационных габаритов.

## Что уже работает, что требует модели

| Возможность | Статус |
| --- | --- |
| Пули, очереди, разные направления, накопление и save/load | Реализовано и проверено в кампании |
| Локальная вмятина с непрерывными швами, нормалями и тенью | Реализовано на исходной оболочке B01; общий меш уплотняется один раз |
| Колёса, фары, защитные трубы, оружие | Реальные имеющиеся детали отделяются в пределах пула |
| Окна машин/зданий | Трещины и тёмный остаток стекла; за ними исходная сплошная оболочка |
| Сквозной визуальный след снаряда | Shader-discard; нет толщины среза, нового тоннеля collision mesh или расчёта выхода пули |
| Двери, капот, бронепанели | Нужны отдельные поверхности/внутренние стороны, петли или точки отрыва и ID; в B01 дверь сейчас часть оболочки |
| Полные оконные проёмы | Нужны отверстия в основе, откосы и интерьер; удаление накладного стекла само по себе этого не создаёт |
| Произвольный обвал бетонного здания | Нужны подготовленные разрушенные модули/стыки/изломы; сейчас сохраняется повреждённый остов |
| Контакт машин и остовов | Реальный swept-контакт и нормальная скорость дают локальный удар; неподвижное касание не наносит повторный урон. Полной динамики rigid body нет |

Не менять силуэт, исходные материалы и вооружение ради подключения. Для визуальной проверки: `http://127.0.0.1:8766/campaign/?damage=1`, Shift+клик или выбор части в панели. Проверить обе стороны, крышу, повторные удары, поворот/движение, отрыв, сохранение и возврат с дальнего LOD. Затем выполнить `npm run check:damage` и `npm run check:damage:browser`.

## Освобождение ресурсов

Логическое состояние живёт с объектом миссии. При удалении объекта его строка атласа возвращается в свободный список; загрузка другого объекта с тем же ID заново привязывает запись. Геометрия прототипа и BVH общие для типа/LOD, а не для экземпляра. Материальные hooks здания освобождаются через `releaseBuilding`; косметические обломки освобождают выделенные geometry/material при истечении срока и вытеснении. При добавлении новых render layers необходимо сохранить этот жизненный цикл, включая выгрузку и повторную загрузку миссии.
