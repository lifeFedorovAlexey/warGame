# Бюджет кадра: замер перед оптимизацией

- **Дата:** 2026-11-12.
- **Ветка:** `perf/frame-budget-20261112`.
- **Состояние:** измеряем, ничего в игре не меняем.

## Зачем

Известно общее число вызовов отрисовки (772 в бою M01, 744 в M02) и общий
профиль процессора, но неизвестно, **кто** даёт эти вызовы: постройки,
терраин, дороги, декорация, машины или теневой проход. Без этой разбивки
оптимизация начинается с догадки и легко уходит в неправильные 10%.

## Метод

`tools/measure-frame-budget.mjs` ставит игру на паузу на штатном сейве и
фиксирует масштаб рендера 1. Дальше:

1. **Стоимость отрисовки** — 60 кадров подряд, отдельно от симуляции.
2. **Теневой проход** — один кадр без обновления тени и один с принудительным
   обновлением; разница вызовов и треугольников и есть стоимость теней.
3. **Разбивка по категориям** — по очереди скрывается каждый прямой потомок
   сцены, сцена рендерится заново, разница `renderer.info.render` записывается
   в категорию. Дополнительно считается число мешей, материалов и объектов,
   которые отбрасывают тень.
4. **Симуляция** — 60 фиксированных шагов `mission.advance(1/60, {budgetMs: 5})`
   тем же бюджетом, что в игре.
5. **Кадр целиком** — 60 вызовов `world.update(...)`, то есть всё, что игра
   делает за кадр, кроме обработки ввода и интерфейса.

Сима замеряется последней: она двигает состояние, а предыдущие пункты должны
описывать сцену, которую игрок видит сразу после загрузки.

## Запуск

```powershell
python tools/serve.py
npm run measure:frame-budget                    # m01 и m02
node tools/measure-frame-budget.mjs --missions m02
```

Параметры: `--url`, `--missions`, `--out`. Переменные окружения:
`WARGAME_URL`, `PERF_MISSIONS`, `PERF_OUT`, `PLAYWRIGHT_PATH`, `EDGE_PATH`.
Печать сводки идёт в консоль, отчёты — в `campaign/reports/frame-budget/`
(каталог не отслеживается git).

## Что в отчёте

| Поле | Смысл |
| --- | --- |
| `draws.main` | вызовы и треугольники обычного прохода |
| `draws.shadow` | разница при принудительном обновлении тени |
| `draws.withShadow` | полный кадр: обычный проход плюс тени |
| `frame.render` | стоимость отправки отрисовки, мс |
| `frame.world` | стоимость полного кадра игры, мс |
| `frame.simulation` | стоимость шага симуляции, мс |
| `census` | материалы, шейдерные программы, геометрии, кастеры, объекты |
| `categories` | вызовы, треугольники, меши, материалы и кастеры по каждой ветви сцены |
| `entities` | число машин и построек по типам |

## Ограничения метода

- Сцена на паузе и стартовой камере: это стоимость загрузки сцены, а не боя.
  Динамику боя по-прежнему показывает `check-playtest-performance-browser.mjs`.
- Замер одного компьютера и одной сборки; сравнивать можно только одинаковые
  условия (тот же сейв, `renderScale = 1`, та же видеокарта).
- Скрытие ветви сцены убирает и её тени, поэтому вклад категорий в теневой
  проход оценивается по колонке `casters`, а не по разнице вызовов.

## Уже известные цифры

Замеры 11.11 (1440×900, `renderScale = 1`, RTX 4070): бой M01 — p50 18.1,
p95 23.5, p99 26.0, max 34.8 мс, 772 вызова; бой M02 — p50 21.7, p95 32.2,
p99 42.1, max 87.1 мс, 744 вызова; отход M02 — p50 16.6, p99 27.5, max 60.7 мс.
Замеры 12.11: колонна из 46 машин — p99 17.7 мс и скорость симуляции 0.72 от
реального времени; 500 машин — p50 21.2, p99 54.9 мс, скорость симуляции 0.14.

## Как принимать решения

- Категория с десятками вызовов и большим числом материалов — первый кандидат
  на объединение или инстансинг.
- Рост `census.programs` относительно предыдущего замера означает новые
  варианты шейдеров: искать клонирование материалов и `needsUpdate`.
- Если `draws.shadow` сравним с `draws.main`, а `casters` велик — сначала
  гигиена теней, потом всё остальное.
- Если `frame.simulation` в пределах бюджета, а `frame.render` нет — проблема
  в отправке отрисовки, а не в игровой логике.
